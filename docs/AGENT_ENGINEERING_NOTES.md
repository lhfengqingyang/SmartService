# Agent 工程认知笔记

本文整理 2026-10-23 12:00 之后讨论形成的 Agent 工程认知。实现状态仍以 `PROJECT_STATUS.md` 为准，接口以 `API_CONTRACTS.md` 为准。

## 1. ToolCallingAgent 的实际调用链

```text
用户请求
  -> FastAPI
  -> ToolCallingAgent 将提示词和允许使用的 Tool schema 发给 GLM
  -> GLM 返回工具名称和参数
  -> smolagents 解析并执行 Python Tool
  -> Tool 调用 app.biz 业务函数
  -> 业务函数查询 PostgreSQL 或执行受控写操作
  -> Tool 结果返回 GLM
  -> GLM 生成最终自然语言回答
```

GLM 负责选择工具和参数，smolagents 负责 Loop、协议解析、工具执行和结果回填，业务模块负责最终事实与规则。Tool 不是独立 HTTP 服务，也不是让模型直接执行 Python。

## 2. ToolCallingAgent 与 CodeAgent

- 当前项目使用 `ToolCallingAgent`：模型输出结构化工具调用，由宿主程序执行已注册 Tool，不运行模型生成的任意代码。
- `CodeAgent` 会让模型生成代码，并交给执行器运行；若用于生产，必须关注沙盒、网络、文件系统、依赖和资源限制。
- 因此，`smolagents` 不等于“代码一定在沙盒里运行”。是否运行代码以及隔离程度，取决于 Agent 类型和执行器配置。
- 订单与退款场景参数明确、风险边界清晰，更适合 Tool Calling，而不是开放式代码执行。

## 3. 为什么使用 smolagents

smolagents 提供了通用 Agent Loop：

- 将 Tool schema 提供给模型。
- 解析模型返回的工具名称与参数。
- 执行工具并把 observation 回填给模型。
- 管理步骤数、消息格式、错误传播和最终回答。

如果只使用 OpenAI 兼容 SDK，也可以自己完成这些工作，并不要求必须依赖 smolagents。框架的价值是减少协议适配和基础 Loop 代码，让项目先验证业务闭环；代价是超时、状态、日志和异常语义会受到框架抽象限制。

本项目保留 smolagents 作为可运行基线。后续若为了求职展示实现自研受控 Loop，应与现有 Tool 和业务函数复用，不需要推翻业务层。

## 4. 自研 Loop 的范围与代码量

一个最小自研 Loop 通常需要：

- 消息与工具协议转换。
- 模型调用及工具调用解析。
- 工具白名单、参数校验和执行。
- observation 回填、最大步数和最终答案。
- 超时、异常映射和基础日志。

估算：最小核心约 270～430 行，测试约 200～350 行，总计约 500～800 行。加入持久化状态、完整可观测性、重试、熔断、并发控制、审批和评测后，生产化版本约 900～1600 行或更多。

自研的价值不只是减少依赖，而是能够明确控制状态机、安全边界、总预算、审计结构和故障语义。若只是重新实现框架已有的无限循环，对项目价值有限。

## 5. “受控 Agent”的具体含义

受控不是“参数都可以随便配置”，而是明确谁能控制什么：

- 模型可提供：经过 schema 约束的业务参数，如 `order_id`、退款原因。
- 服务端绑定：`user_id`、租户、角色等身份信息，不能让模型或请求正文任意切换。
- 系统配置：模型名、最大步骤、超时、重试、工具白名单、温度和输出限制。
- 业务层决定：订单归属、退款资格、幂等、并发和数据库约束。
- 用户授权：高风险写操作的明确确认，不由模型代替用户决定。
- 状态机决定：当前阶段允许哪些 Tool、下一步可以进入什么状态。

控制的核心是：模型负责理解和建议，确定性代码负责权限、规则、状态迁移和副作用。

## 6. 最小工具集与意图识别

“不把所有函数都注册给模型”不代表不用模型识别意图。

工具数量少时，可以一次向模型提供当前业务域内全部安全工具，模型在一次推理中选择调用哪个工具，也可以选择不调用。当前项目只有订单查询、退款资格检查和退款准备，因此无需额外路由模型。

工具数量增长后，可采用分层路由：

```text
用户问题
  -> 规则 / Embedding / 小模型 / 主模型做领域路由
  -> 根据权限和会话状态筛选候选 Tool
  -> 将少量 Tool schema 提供给专门 Agent
  -> 主模型完成最终选择和参数生成
```

额外模型 Loop 不是必需步骤。优先使用低成本规则和状态过滤；只有工具规模、描述相似度或多业务域复杂度真正增加时，再引入 Embedding 或路由模型。多意图请求可以让模型在同一 Agent Loop 内依次调用多个候选工具。

## 7. Embedding、对话模型与 pgvector 的分工

- `embedding-3`：将文档片段或用户问题转换为数值向量。
- `glm-4.7-flash`：理解意图、选择 Tool、阅读检索证据并生成回答。
- PostgreSQL + pgvector：保存向量并计算相似度，不负责理解文本，也不是模型。

当前 Embedding 用于 RAG。未来工具达到几十或上百个时，可以将 Tool 描述向量化，先召回少量候选工具，再让 GLM 精选；当前三个工具没有必要增加这层复杂度。

## 8. 查询工具与写操作确认

只读操作可以由模型选择 Tool，但写操作需要更严格的边界：

```text
模型调用 refund_prepare
  -> 检查订单与退款资格
  -> 服务端保存结构化 pending_action
  -> 前端展示确认内容
  -> 用户点击确认
  -> 客户端提交 confirm_pending_action=true
  -> FastAPI 绕过模型，确定性调用 apply_refund()
```

`confirm_pending_action=true` 不是 Tool 参数，也不需要模型再次判断。这样可以避免模型把“我还没确认”等自然语言误判成授权。模型可以解释动作，不能授予自己执行副作用的权限。

当前会话是单进程内存实现，仅用于 MVP。生产环境应使用 Redis 或数据库保存待确认动作，接入可信认证上下文，并记录审计信息。

## 9. 异步接口与线程池

`async def` 和 `await run_in_threadpool()` 不会让一次同步数据库或模型请求本身变快。它们的作用是避免同步 I/O 阻塞 FastAPI 主事件循环，使同一进程可以继续处理其他请求，从而改善并发吞吐和响应性。

当前 Agent 底层是同步调用。API 的总等待超时可以及时返回 504，但不能强制杀死已经在线程池运行的任务。真正的硬取消需要独立工作进程、任务队列或原生异步且支持取消的调用链。

## 10. 生产选型判断

线上可以使用 smolagents，也可以使用 LangGraph、厂商 SDK、自研状态机或企业内部框架。公开项目只能说明一种技术方向，不能据此断言大型公司的内部系统统一使用某个框架。

生产选型主要看：

- 流程是否需要显式状态机和人工审批。
- 工具权限、身份绑定和审计要求。
- 超时、重试、幂等、并发和故障恢复能力。
- 模型供应商切换和协议兼容成本。
- 可观测性、评测和灰度发布能力。

对本项目而言，先用 smolagents 完成真实闭环，再增加一个可对照的受控自研 Loop，比一开始重写全部框架更有展示价值。

## 11. 前端与 Agent 工程师职责

当前工程没有前端，但可以在同一 VS Code 工作区增加 `frontend/`，不需要 Java 或第二套编辑器。建议使用 React + TypeScript + Vite：

- 前端开发服务器：`127.0.0.1:5173`。
- FastAPI：`127.0.0.1:8000`。
- PostgreSQL：Docker Desktop 中运行。

个人项目和小团队中，Agent 开发者经常需要制作轻量演示页面；中大型团队的生产 UI 通常由前端工程师实现。Agent 工程师仍需定义好流式协议、`conversation_id`、Tool 状态、知识来源、错误码以及确认/取消协议。

最小客服演示前端预计约 900～1800 行。源码与构建产物较小，额外磁盘主要来自可重建的 `node_modules`，整体约 300～800 MB。

## 12. 当前项目的面试表达

可以用以下顺序说明：

1. 使用 FastAPI 提供 RAG、订单和退款接口，PostgreSQL 同时承载业务数据与 pgvector 检索。
2. 使用真实 Embedding 和 GLM，RAG 严格以检索证据回答，并在 SQL 内完成 ACL 过滤。
3. 使用 smolagents 验证工具调用闭环，但 Tool 只调用业务层，不允许模型绕过业务规则直接操作数据库。
4. 对退款采用“模型准备、用户授权、服务端执行”的结构化确认状态机，并使用幂等键和数据库约束兜底。
5. 清楚说明 MVP 限制：身份仍来自请求参数、会话是单进程内存、同步 Agent 无法硬取消、免费模型可能限流。
6. 下一步通过真实端到端演示、评测集、文档列表/删除和可选前端完成交付。
