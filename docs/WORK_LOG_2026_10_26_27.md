### RAG/Agent 质量如何判断

- 建立固定种子样本、离线评分、人工逐条复核、运行指标、显式反馈、负反馈待标注队列及检索阈值实验。当前 30 条项目种子案例由项目内部复核；真实用户负反馈可入集的记录为 0，不应称为已运营出真实标注集。
- 检索看来源命中、片段命中、Top-1 分数、前两名分差、空检索比例、ACL 过滤等；回答看引用格式、事实是否被对应片段支持、拒答是否正确；Agent 还看工具选择、参数、订单归属、待确认动作和越权/误写。HTTP 错误单列可用性，不计入回答质量分母。结构指标不能代替人工事实核对。
- “无用”反馈的处理路径：在线反馈带 `request_id` → 离线幂等同步待审队列 → 人工查看原问题、证据和失败类型 → 审批并补预期标签 → 私有固定评测集 → 修改知识、分块、检索、提示词或规则 → 同集回归及前后对比。这不会自动训练或更新 LLM 权重。线上通常由异步/定时任务和运营标注平台承接，当前项目只有轻量本地队列与命令行审核能力。
- A/B 实验只说明两个检索配置的观测差异；要证明改进，需相同问题/标注口径、可用性与质量分开统计，且复核事实与回退风险。现有报告自对比仅验证比较器工作，不代表效果提升。

### 当日模型阻塞与排查

- 智谱 `embedding-3` 真实请求返回 200，向量维度实测为 1024；`glm-4.7-flash` 聊天多次返回 429 / `1305`，有证据的 RAG 进到生成阶段后应用返回 502。关闭 SDK/smolagents 重试后能较快失败，避免重试放大。没有把 429 当作“权限不足”或把 HTTP 200 当作答案正确。
- 固定样本的旧观测中存在上游失败；不能把全部失败案例逐条推断为 429。人工复核发现旧 Agent 回答的“回复确认即可执行”文案误导，已改为服务端固定确认说明。仍需真实新基线。

### 求职展示与后续技术方向

- 讨论后的项目定位是可运行的智能客服 Agent 演示：FastAPI、真实 Embedding、PostgreSQL/pgvector RAG、ACL 检索、smolagents 工具调用、模拟退款确认、离线评测与反馈闭环。简历可如实描述已实现能力；不得把规划中的 MCP、熔断、可信身份、跨实例会话或“企业级线上平台”写为完成。
